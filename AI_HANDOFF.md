## Запрос и принятые решения

Пользователь заказал демо сервиса отдела аренды Stay Property, затем полный функционал. Гость сканирует QR в квартире, получает Wi-Fi, адрес/маршрут домой, телефон управляющего, инструкции и полезные места рядом. На этой же странице размещается баннер Stay Property с лид-магнитом «Подберём 3 квартиры под ваш бюджет», чтобы заинтересованные арендаторы могли обратиться по покупке недвижимости. Пользователь одобрил визуальный рендер: светлая мобильная страница, оранжевые акценты, фотографии и три сценария — главная, места рядом, подбор недвижимости.

Обязательные дополнения пользователя: админка, отправка заявок в Telegram, CRM позже (доступа сейчас нет). Последние уточнения пользователя имеют приоритет: менеджер должен быть персональным менеджером **по аренде**, с фото, именем и WhatsApp; показывать его на главной и в помощи по проживанию. **У каждого клиента свой менеджер из админки**: добавлен раздел «Гости и заезды» с отдельными персональными ссылками/QR и назначением managerId. Убрать фразы «Контакт уточняйте при заселении» и инструкции гостю про настройку админки. В разделе покупки **убрать любые карточки менеджеров и прямые контакты**, оставить форму, чтобы все обращения на подбор учитывались в сервисе. Старое пожелание о менеджере по покупке отменено. Пользователь отдельно попросил создать этот документ с описанием сделанной работы. Не заменять админку статичным макетом и не выдавать неподключённый Telegram за рабочую доставку.

## Реализация

Локальный проект без фронтенд-фреймворка и без сборки. Node.js 24, ES modules, встроенный HTTP-сервер, единственная внешняя зависимость `qrcode` (зафиксирована package-lock.json). Данные в `data/store.json`, запись через временный файл и rename. CRUD синхронный, рассчитан на один процесс демо; не подходит для нескольких серверов/реплик.

Файлы:

- `server.mjs`: HTTP, статические файлы, публичный API, auth админки, CRUD, QR, очередь отправки Telegram.
- `seed.mjs`: начальные данные квартиры, комплекса, управляющего, менеджера, мест и баннера.
- `public/app.js`: гостевые экраны, RU/EN интерфейс, модальные инструкции/контакты, формы, копирование Wi-Fi, фильтры мест.
- `public/admin.js`: вход, обзор, квартиры, комплексы, контакты, места, баннер, заявки и статусы, CSV, QR/печать, инструкция подключений.
- `public/ui.js`: escaping HTML, SVG-иконки, fetch, toast и dialog.
- `public/styles.css`, `public/personal.css`, `public/admin.css`: адаптивный дизайн, карточка персонального менеджера и печатные стили.
- `public/assets/apartment.jpg`, `residence.jpg`, `manager.jpg`: локальные иллюстративные фото Unsplash. Портрет условный, не реальный сотрудник Stay Property.
- `.env.example`: все настройки сервера; `.env` с секретами не создавать из выдуманных значений.
- `tests/integration.test.mjs`: интеграционная проверка основного пути и защиты данных.
- `README.md`: запуск, демо-доступ, подключение Telegram, ограничения.

## Запуск / доступ

`npm.cmd install`, `npm.cmd run dev`. Гостевая страница `http://localhost:3000/g/demo`, админка `http://localhost:3000/admin`. Локальный демо-логин `admin`, пароль `StayDemo2026!`. Это известные демонстрационные значения, не реальные секреты компании. По умолчанию HOST=127.0.0.1. При запуске на другом интерфейсе сервер требует уникальный ADMIN_PASSWORD. Для QR на телефоне нужен реальный PUBLIC_BASE_URL, доступный этому телефону; localhost для этого не подходит.

В текущей сессии для просмотра браузером сервер запускался через скрытый Start-Process (node.exe server.mjs) с логами `data/server.log`, `data/server-error.log`. Если порт занят, не запускать второй экземпляр и не завершать все node.exe подряд: проверить процесс конкретного server.mjs из этой папки. Встроенный npm dev в изолированном Windows sandbox был недоступен браузеру; запуск вне sandbox через штатное согласование решил это.

## API и модель

Публичные: GET `/api/guest?token=...`, POST `/api/leads`, GET `/api/health`.

Админские: POST `/api/admin/login`, POST `/api/admin/logout`, GET `/api/admin/data`; POST/PUT/DELETE `/api/admin/{apartments|complexes|contacts|places|stays}/[id]`; PUT `/api/admin/banner`; PATCH/DELETE `/api/admin/leads/:id`; POST `/api/admin/leads/:id/retry`; GET `/api/admin/qr/:apartmentId`; GET `/api/admin/stay-qr/:stayId`.

Квартира ссылается на комплекс, hostId (управляющий) и managerId (персональный менеджер по аренде). Оба типа обращений записывают managerName персонального менеджера по аренде, при отсутствии — управляющего. Это внутренняя привязка; контактов в покупке нет. Места привязаны к комплексу. Общий баннер. При создании квартира получает случайный 36-символьный токен, при редактировании токен сохраняется. Единственная начальная публичная ссылка `/g/demo` специально демонстрационная. Удаление контакта/комплекса, на который есть ссылки, запрещено; последнюю квартиру удалять нельзя.

Заезд (stays) содержит имя гостя, apartmentId, managerId, даты arrival/departure и собственный постоянный token. /api/guest сначала ищет заезд по токену и выбирает его менеджера, затем — общую квартиру по её токену. Заявка сохраняет stayId и guestName, если пришла с персональной ссылки. В существующую базу добавляется пустой stays без сброса данных. Даты справочные, доступ не истекает автоматически. Печатный общий QR квартиры показывает базового менеджера квартиры; для разных менеджеров у разных гостей нужны персональные ссылки/QR заездов. Не утверждать, что анонимная общая ссылка сама распознаёт клиента.

Заявка имеет тип sales/service, контакт, цель, бюджет/сообщение, снимок названий квартиры/комплекса/района/ответственного, источник, дату, согласие и его версию, рабочий статус new/in_progress/done и независимый статус Telegram. Перед отправкой в Telegram заявка сохраняется. Статусы доставки: not_configured/pending/sending/sent/failed. Токен Telegram и ID чата — только в окружении сервера. Автоповторы каждые 30 секунд с задержкой после ошибок. У Telegram sendMessage нет используемого здесь ключа идемпотентности: после неоднозначной сетевой ошибки возможен дубликат с тем же ID заявки. При повторной отправке успешно доставленная заявка не отправляется заново. После настройки Telegram ранее накопленные неотправленные записи будут отправлены автоматически — учитывать при тестах.

Админские сессии в памяти, HttpOnly SameSite=Strict cookie, scrypt-проверка пароля, CSRF-токен в mutating API. Перезапуск требует повторного входа. Гостевой API не выдаёт заявки, настройки и другие квартиры. Все HTML-значения экранируются. Ссылки на фото/маршруты принимают HTTPS или локальные /assets/. Телефон валидируется; CSV экранирует формулы. Ограничение запросов на логин и заявки. CSP без inline-script.

## Незавершённое / следующий этап

- Настройки реального Telegram пользователь ещё не предоставил; реальной отправки не было. Не спрашивать токен в открытом чате, пусть добавит его в .env.
- CRM не подключена, доступ отсутствует. Не делать вид, что сохранение локально равно интеграции CRM.
- Реальные номера управляющего и персонального менеджера по аренде отсутствуют. В гостевом интерфейсе честное сообщение; после ввода в админке появляются tel и WhatsApp только для обслуживания проживания. В покупке не добавлять прямые контакты.
- Места рядом — демонстрационные поисковые ссылки, не проверенная геобаза/расстояния/часы. Уточнить настоящие места для объектов.
- RU/EN переведены интерфейс и часть демо-текстов. Произвольный контент админки одноязычный. Нужна модель переводов для полноценной версии.
- Фото меняются по ссылке, загрузки файлов пока нет.
- Нет учёта открытий/кликов, отдельных пользователей/ролей, аудита правок, полноценной БД, резервных копий, ротации гостевых токенов.
- Нужны утверждённые политика/согласие и срок хранения данных перед реальными клиентами. В демо показано короткое честное уведомление.
- Публичная публикация не выполнялась: пользователь работает в локальной папке проекта, демо открыто локально. Перед размещением выбрать хостинг, HTTPS, уникальные админские учётные данные и проверенные данные квартиры.
